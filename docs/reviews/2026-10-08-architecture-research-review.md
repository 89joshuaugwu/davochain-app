# Architecture and research review - 8 October 2026

The current arrangement agrees with the boss's **feature-first option**, but it does not yet implement the boss's full separation of presentation, domain and data. This is a working frontend preview with useful shared infrastructure and tests. It should mature incrementally rather than be described as a completed clean architecture or rewritten merely to match folder names.

Paths below are relative to the app root (`davochain-app/`) unless stated otherwise. Scope: all of `../research.txt` was read; the three supplied rendered PDF pages in `../tmp/boss-pdf-pages/` were visually inspected; `lib/`, `pubspec.yaml`, `README.md`, `DEVELOPMENT_CONTEXT.md`, the mobile-experience plan, v12 work log and selected historical logs were inspected. This is a read-only source/document review, apart from this report. Other work was occurring concurrently; this report is not a fresh analyzer, test, build, device or Figma verification.

## Boss guide mapped to the app

| Boss's responsibility | Current evidence | Assessment |
| --- | --- | --- |
| Tiny entry point and root app configuration | `lib/main.dart` bootstraps Flutter; `lib/app.dart` owns `MaterialApp`, theme and named entry routes | Aligned. First-frame readiness and orientation are bootstrap concerns. |
| Shared infrastructure in core | `core/theme/app_theme.dart`, `core/navigation/`, `core/preview/preview_account_state.dart` | Theme/navigation are aligned. The preview account notifier is session demo state; move it into its owning feature when account state becomes substantive. |
| Feature-first alternative | `features/auth`, `crypto`, `buy_crypto`, `gift_cards`, `profile_settings`, `transactions`, `dashboard`, `onboarding` | Explicitly permitted by PDF page 2. No need to flatten these into global data/domain/presentation folders. |
| Thin screens, reusable widgets, state controllers | Most feature code lives in `presentation/`; shared PIN, date picker, auth controls and trade layout exist | Partially aligned. Several flow files contain many screens, calculations, selections and sample data. Crypto/profile files exceed 100 KB; size is a refactoring signal, not itself a defect. |
| Pure Dart domain entities, repository contracts and business actions | No feature `domain/` boundaries were present at inspection | Missing for production architecture. `buy_crypto_models.dart` imports Flutter `Color`, stores fixture balances/rates and computes conversions; it is a presentation/demo model, not a framework-independent domain entity. |
| Data sources, DTOs and domain repository implementations | No feature `data/` boundaries, HTTP client or repository implementations were present | Backend-ready data architecture is still future work. UI success does not demonstrate server execution. |
| Routes and guards | Root named routes plus shared `AppPageRoute` and feature-local Navigator calls | Real preview navigation exists. Authentication guards and deep-link/production routing requirements remain undefined. A `routes/` folder name or GoRouter is not required merely for compliance. |
| Assets, native shell and tests | Declared image/font directories, Android/iOS runners, focused tests in `test/` | Substantially aligned. Tests use descriptive filenames rather than mirroring every feature directory; useful coverage matters more than exact naming. |

The boss's important rule is the **direction of dependencies**: presentation consumes domain contracts, data implements those contracts, and domain stays free of UI/data imports. Installing Bloc, Riverpod, Dio or get_it would not establish that rule on its own. Flutter's own [architecture guide](https://docs.flutter.dev/app-architecture/guide) also separates UI and data responsibilities and treats a domain layer as conditional on complexity; the boss's stricter domain requirement remains the project direction.

There is no evidence for calling this structure universally better than the boss's example. Feature grouping helps locate related screens; explicit boundaries help test rules, replace mock services and connect APIs safely. The current version favors rapid screen iteration, with larger files and coupled fixture logic as the cost.

## Research: useful leads, several overstated claims

The file spans motion, styling, networking/state, security, persistence/sync, performance, background work, QA and release tooling. Its unlinked numbered citations and descriptions such as “best,” “ultimate,” “gold standard” and “zero frame drops” are not comparative evidence or guarantees. It is a candidate list, not an installation plan.

| Lead | Verified capability and correction | Decision for this app |
| --- | --- | --- |
| Riverpod | Supports provider-based state/dependency sharing and asynchronous state. Code generation is [optional](https://riverpod.dev/docs/concepts/about_code_generation). [Automatic disposal](https://riverpod.dev/docs/concepts2/auto_dispose) depends on configuration; controllers/network resources need appropriate cleanup. AsyncValue represents loading/error/data; the app still designs those UI states. It is not the HTTP transport. | Consider when shared async feature state is introduced; compare against the boss's Bloc/Cubit direction. Keep local ephemeral widget state where appropriate. |
| Dio and Retrofit | [Dio](https://pub.dev/packages/dio) supports interceptors, cancellation, timeout and transfer progress. Caching needs a chosen policy/custom interceptor or plugin; superiority over `http` is not established. [Retrofit](https://pub.dev/packages/retrofit) generates Dio-backed clients; generated types do not prove endpoint URLs or server payloads are correct. | Choose after API contracts, token-refresh, cancellation and error requirements exist. Retrofit is optional additional generation, not a prerequisite. |
| Rive | [Official Flutter runtime](https://rive.app/docs/runtimes/flutter/flutter) loads authored Rive files and drives artboards/state machines. | Useful if an approved interactive `.riv` asset is delivered. No such requirement is established by the current welcome sequence. |
| Lottie | [Package documentation](https://pub.dev/packages/lottie) describes a pure Dart renderer for Bodymovin JSON. Default playback follows the composition frame rate; device-rate playback is configurable, not a promise of 120 FPS. A dotLottie archive can require a custom decoder/file picker. | Useful for approved authored illustration animation, with asset/device QA. Not needed for the implemented logo reveal. |
| flutter_animate / animations | [flutter_animate](https://pub.dev/packages/flutter_animate) supplies chainable widget effects. Flutter's [animations package](https://pub.dev/packages/animations) supplies Material motion patterns; container transform is exposed through [`OpenContainer`](https://pub.dev/documentation/animations/latest/animations/OpenContainer-class.html), not a general `ContainerTransform` widget assumed from the prose. | Existing splash uses an AnimationController and existing routes honor reduced motion. Keep them unless a concrete approved interaction needs a different tool. |

Security research needs the strongest correction: no package stack can “lock down completely” a client. [Flutter obfuscation](https://docs.flutter.dev/deployment/obfuscate) renames symbols; it does not encrypt resources or protect against reverse engineering. [Envied's own documentation](https://pub.dev/packages/envied) says embedded obfuscated values can still be recovered. `.env` exclusion and compile-time injection do not make privileged backend secrets safe to ship. The boss's `.env` guidance should be read as configuration hygiene, not secret protection.

[Secure storage](https://pub.dev/packages/flutter_secure_storage) is a candidate for session tokens after authentication design; its guarantees vary by platform/configuration and should not be called universally hardware-isolated. Pinning, biometrics and root detection require a specific threat model and operational policy, not automatic installation or destructive client behavior. Client PIN screens currently demonstrate input only; server authorization and transaction integrity remain backend work.

Persistence choices should follow required offline behavior and data relationships. The research's built-in Isar AES-256 claim was not established from the official documentation inspected; do not rely on it without verifying the exact maintained package/version. Firebase Firestore has documented [offline persistence](https://firebase.google.com/docs/firestore/manage-data/enable-offline); this does not establish identical built-in Supabase behavior. Offline financial mutations need explicit conflict/idempotency rules, rather than assuming automatic sync makes payments correct.

The performance advice is directionally useful: profile on actual hardware and measure before optimizing. [Flutter profiling guidance](https://docs.flutter.dev/perf/ui-performance) uses roughly 16 ms at 60 Hz; 120 Hz allows roughly 8.3 ms. The statement that Flutter runs *everything* on one thread is too broad: UI Dart uses the main isolate, with engine/raster/platform work elsewhere. Native [compute](https://api.flutter.dev/flutter/foundation/compute.html) uses a separate isolate; on web it uses the current event loop. Neither isolates nor Impeller guarantee smooth frames. Background jobs are OS-scheduled and cannot guarantee a precise 2 AM run. Testing and CI suggestions are options to evaluate after their actual requirements; none of the listed extra tools is mandatory for this preview.

## Staged next steps

1. Finish the authorized preview repairs and verify reachable states, keyboard/text scaling, back/cancel, reduced motion and device behavior. Preserve completed v12 decisions unless a mismatch is reproducible. Keep demonstrations explicit.
2. Refactor one substantive feature first, such as Buy Crypto: small screens/widgets plus a controller; pure Dart order/quote rules and a repository contract; deterministic mock repository implementation. Separate asset colors/paths from domain values. Test amount rules and cancellation/error transitions without rendering the whole app.
3. Confirm backend contracts and then implement data DTOs, authenticated transport, repository mapping and server error handling behind that contract. Select one state-management approach and only the dependencies those requirements justify. Add token storage and production security policies with the backend.
4. Add persistence/background sync only for specified offline requirements; profile expensive screens before adopting more motion. Establish release signing and repeatable CI checks once deployment ownership is agreed.

This preserves feature-first organization while moving toward the boss's actual responsibilities. Empty layer folders or package installation alone would not constitute progress.
